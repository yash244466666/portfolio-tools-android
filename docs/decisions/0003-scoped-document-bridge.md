# ADR 0003: Scoped Android Document Bridge

- Status: Accepted
- Date: 2026-09-05
- Owner: Yash Sikdar
- Revisit when: an enabled tool needs native streaming reads, generated output above 5 MiB, retained document access, or multiple simultaneous system document operations.

## Context

Android file-based tools need user-directed import and export without broad storage or media permissions. The web runtime can use browser `File` objects and downloads, but Android must preserve `content://` URIs and use the system document UI. Capacitor also logs bridge arguments in debug builds by default, which is incompatible with the rule that file contents and sensitive filenames never enter logs.

## Decision

Add the app-owned, version-1 `DocumentFiles` Capacitor plugin with only three operations:

- `pickDocuments` launches `ACTION_OPEN_DOCUMENT` with `CATEGORY_OPENABLE` and returns bounded, validated metadata plus `content://` URIs. It does not copy content or retain URI access.
- `saveDocument` launches `ACTION_CREATE_DOCUMENT` for a generated file already staged under the private `cache/save/<operation-id>/` directory. Native code resolves that exact location, opens the selected destination in explicit write-and-truncate (`wt`) mode, streams the output off the main thread, and deletes the staged file when the operation settles.
- `discardSave` removes the exact staged operation after cancellation or adapter failure.

Every request carries bridge contract version `1` and a UUID operation ID. The plugin allows only one active system document operation, validates all arguments again in Java, accepts at most 32 MIME filters and 20 selected documents, defaults picker size to 50 MiB, and enforces a 100 MiB hard picker metadata limit. Generated Save As handoffs are limited to 5 MiB; larger output requires a later native streaming design rather than increasing bridge payloads.

Capacitor Android logging is disabled for every variant so official plugin calls cannot put clipboard values, generated bytes, or filenames in Logcat. The app adds no storage/media permission, directory-tree grant, inbound file intent filter, exported component, dependency, native library, FileProvider path, or ProGuard rule.

## Alternatives considered

- Broad storage or media permissions: rejected because system pickers grant access to the user-selected document without expanding the manifest permission budget.
- Browser download behavior inside WebView: rejected because it is not a dependable Android Save As workflow.
- Passing generated Base64 directly to the custom picker call: rejected because Capacitor persists activity-call arguments for recreation and debug logging can expose arguments.
- Persisting every selected URI grant: rejected because current imports are immediate operations and do not require silent long-term access.
- Returning arbitrary filesystem paths: rejected because it would widen the native bridge and break the `content://` contract.

## Consequences

- Picker cancellation, invalid metadata, size failures, concurrent operations, Save As cancellation, and write failures have stable typed codes.
- Unknown document sizes or MIME types outside a requested wildcard are rejected instead of guessed from filenames.
- Save As can recover its private staged source after Activity recreation; if no JavaScript callback survives, Capacitor reports the restored result to the rebuilt web session.
- A provider may leave a partial destination if it rejects deletion after a write failure; the adapter reports failure and never deletes or changes the source document.
- File-consuming tools must add a separate reviewed content-URI streaming operation or a strict bounded import-copy operation. This picker does not make content URIs readable from JavaScript.
- System-picker and process-recreation behavior still requires instrumentation/UI Automator and physical-device evidence before release.
